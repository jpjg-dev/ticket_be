# Kafka Outbox 회귀·장애 테스트

## 목적

결제 Outbox와 Audit Consumer 도입이 정합성을 유지하는지 확인하고, 제한된 운영 자원에서 동기 요청 경로에 미치는 비용을 분리해 측정합니다. Kafka는 처리 속도를 높이기 위한 기능이 아니라, 결제 확정 이후 이벤트를 유실 없이 전달하고 독립적으로 재처리하기 위한 경계입니다.

## 환경과 비교 기준

- 측정일: 2026-08-28
- 부하 스크립트: `performance/k6/popular-event-payment-arrival-rate-spike.js`
- 요청 부하: 50초 동안 최대 `1,000 iterations/s`
- 서비스 자원: backend, PostgreSQL, Redis, Kafka, Prometheus, Grafana가 CPU `0,1`을 공유합니다.
- 외부 부하 자원: k6와 Mock PG는 서비스 CPU 집합 밖에서 실행합니다.
- 비교 기준: 2026-07-22의 `post-lock-measured-1~3.json`을 가장 가까운 pre-Outbox 기준선으로 사용합니다.

과거 기준선과 현재 측정은 동일한 부하 스크립트·좌석 1,000개·2 vCPU 제약을 사용하지만 같은 commit의 A/B 측정은 아닙니다. 따라서 차이는 방향성 판단에 사용하고, Outbox 하나의 순수 비용으로 단정하지 않습니다.

## 비용 분리

Kafka broker, Relay와 Audit Consumer를 끄고 동기 트랜잭션의 Outbox INSERT만 유지한 warm 진단 결과는 다음과 같습니다.

| 완료 결제 | 전체 여정 p95 | 좌석 조회 p95 | 예약 p95 | 결제 준비 p95 | 결제 승인 p95 | dropped |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 3.97s | 1.33s | 2.42s | 2.07s | 2.14s | 453 |

이 진단은 한 번만 실행했으므로 최종 기준선이 아니라 원인 분리용입니다. 동기 Outbox INSERT에도 비용은 있지만, 전체 Kafka 경로보다 회귀 폭이 작았습니다.

Prometheus에서 전체 Kafka 경로 실행 중 다음 최대값을 확인했습니다.

| 지표 | 최대값 |
| --- | ---: |
| 시스템 CPU | 100% |
| backend process CPU | 84.6% |
| Hikari active | 10 |
| Hikari pending | 188 |
| Outbox PENDING backlog | 803 |
| 가장 오래된 PENDING | 57s |

현재 회귀는 단일 쿼리나 직렬화 하나보다, 2 vCPU 안에서 사용자 요청·Outbox Relay·Audit Consumer·Kafka broker가 CPU와 DB connection을 함께 경쟁한 영향으로 해석하는 것이 타당합니다.

## 장애 복구 검증

- Kafka broker를 실제 pause한 상태에서 발행하면 Outbox가 `PENDING`을 유지하고 retry가 예약됩니다.
- broker를 unpause한 뒤 재실행하면 동일 이벤트가 `PUBLISHED`로 전환됩니다.
- 같은 `eventId` 재수신은 Inbox에서 중복 제거합니다.
- malformed record는 DLT로 격리하고 같은 partition의 후속 정상 record는 계속 처리합니다.
- DB 장애는 offset을 진행하지 않고 같은 record를 재전달합니다.

## 판단

- 정합성·복구 목적은 달성했습니다.
- 현재 단일 2 vCPU 배치에서 Kafka 후처리를 무제한으로 요청 경로와 경쟁시키는 구성은 성능 회귀가 큽니다.
- DB pool을 먼저 늘리면 CPU 포화 상태에서 경합만 키울 수 있으므로 우선순위가 아닙니다.
- 다음 조정은 Relay batch/주기와 Consumer 처리량을 CPU·Hikari pending·backlog 기준으로 제한하거나, Kafka broker/후처리 worker의 자원을 요청 경로와 분리하는 방향으로 진행합니다.
- 대기열은 사용자 요청 유입을 제어하고, Relay 제한은 이미 커밋된 backlog의 배출 속도를 제어하므로 두 보호 장치를 별도로 관측합니다.

## 2026-09-01 처리율 후보 재측정

동일 2 vCPU 환경에서 Relay batch `5/10/20`과 Audit Consumer idle `0/100ms`를 단계적으로 비교했습니다. 하지만 backend 재기동 뒤 같은 `20/0ms` control도 완료 결제가 `505 -> 869 -> 1,000`으로 크게 변해 후보 간 차이보다 warmup·host 변동이 더 컸습니다.

- `20/0ms`: 세 번째 실행에서만 완료 결제 `1,000`, unexpected `0`을 충족했습니다.
- `5/0ms`: warm 재측정에서도 완료 결제 `615`, unexpected `34`로 탈락했습니다.
- `10/0ms`: warm 재측정에서도 완료 결제 `702`로 탈락했습니다.
- `20/100ms`: 재기동 직후 실행에서 완료 결제 `328`로 탈락했습니다.

후보가 정확성 기준을 통과하지 못했고 설정별 재기동 warmup 편향을 제거하지 못했으므로, Consumer `50ms`와 최종 후보 3회 측정은 진행하지 않았습니다. 현재 운영 시작값은 Relay batch `20`, Consumer idle `0ms`로 유지합니다. 이는 최적값 확정이 아니라 근거가 부족한 변경을 피한 결정입니다.

다음 재측정은 후보마다 full arrival warmup을 반복해 control 수준이 안정된 뒤 점수화하고, fixture 초기화 전에 Outbox backlog 수렴 또는 backend 중지를 보장해야 합니다. 상세 실행값과 무효 처리 근거는 Git 제외 private 문서에 보관합니다.

## 2026-09-05 기준 설정 재검증

최신 소스의 `bootJar`를 확인하고 테스트 Compose를 기동했습니다. smoke 결제 1건과 인증 사전 검증을 통과한 후, 토큰 갱신·fixture 초기화·readiness를 실행마다 적용해 기준 설정을 3회 재측정했습니다.

3회 모두 클라이언트 결제 완료 1,000건과 unexpected 0건을 충족했습니다. 하지만 동일 설정에서도 journey p95와 dropped iteration이 실행 순서에 따라 계속 감소해, 안정된 성능 기준선이나 후보 간 우열을 확정할 근거로 사용하지 않습니다. 상세 수치와 원본 결과 경로는 private 문서에 보관합니다.

테스트 서비스는 CPU `0,1`을 공유하고 별도 Mock PG·k6를 사용했습니다. 같은 호스트에 기존 Kafka·모니터링 스택도 실행 중이었으며, 기존 Kafka의 높은 CPU 사용 샘플과 낮은 사용 샘플이 모두 관측됐습니다. 그 존재만으로 회귀 원인을 단정하지 않으며, 호스트 경쟁과 워밍업 영향을 추가 분리해야 합니다.

이번 검증에서는 smoke/arrival의 완료 건수 조건을 분리하고 0건 카운터를 명시적으로 기록하도록 보완했습니다. 승인 결제부터 시작해 이벤트 누락, 전달 hash, 좌석·예매 상태와 중복 활성 좌석을 대조하는 읽기 전용 SQL도 추가했습니다.

운영 시작값은 유지하며 #71은 열어 둡니다. 다음 단계는 동일한 호스트 부하 조건에서 기준선 안정성을 확보한 후 Relay·Consumer 후보 비교와 최종값 선정을 완료하는 것입니다.

### 기존 스택 중지 후 추가 확인

사용자 승인으로 기존 Kafka·모니터링 스택을 일시 중지하고 동일 기준 설정을 3회 더 측정했습니다. 모든 실행에서 결제 완료와 Outbox/Inbox/Audit은 각각 1,000건으로 수렴했습니다. 두 번째와 세 번째 실행의 확장 SQL 검증도 이벤트 coverage 오류·상태 불일치·중복 활성 좌석 0을 확인했습니다.

세 번째 실행은 unexpected가 발생해 합격하지 못했습니다. 따라서 후속 후보 부하 실행을 중단하고 운영 시작값을 유지했습니다. 후보 설정으로 백엔드를 재생성한 직후 사전 gate가 중단시켰으며, 기본 설정과 기존 Kafka·모니터링 컨테이너를 복원했습니다.

원본 summary는 오류 사유별 태그를 보존하지 않아 unexpected의 정확한 원인은 아직 확정하지 못했습니다. 다음 재현에서는 k6 원본 시계열 또는 오류 사유별 집계를 보존하고, 기준선 오류를 해결한 뒤 후보 비교를 재개합니다. 기존 스택 중지가 성능 회귀를 해결했다는 결론은 내리지 않습니다.

## 2026-09-08 진단 진행 상태

후속 재현에서는 공연 목록 조회의 HTTP 503과 `CACHE_TEMPORARILY_UNAVAILABLE` 응답을 확인했습니다. 거부 사유별 메트릭을 추가한 별도 실행에서는 실행 전후 차이로 `refresh_timeout`이 증가해, 해당 실행의 오류가 캐시 재생성 대기 초과 경로임을 확인했습니다. 이 증거로 이전 실행의 unexpected 전체가 같은 원인이었다고 소급 판단하지 않습니다.

### 확인된 범위와 미확인 범위

- 확인: 같은 key의 재생성 락을 얻지 못한 요청이 캐시 값을 기다리다 대기 한도를 넘으면 503을 반환합니다. DB 로드 용량 부족과 인터럽트도 같은 응답 코드를 사용하므로 응답 코드만으로 원인을 구분하지 않습니다.
- 미확인: 실패 순간의 정확한 TTL 만료 시점, 재생성 소요 시간, CPU 스케줄링 기여도는 해당 재현에 기록되지 않았습니다. 느린 SQL이나 TTL 만료만을 최종 원인으로 단정하지 않습니다.
- 추가 계측 완료: 재생성 소유자의 `database_load`와 `cache_write` 시간을 구분합니다. 각각 순수 SQL 시간이나 Redis 네트워크 시간은 아니며, 측정 범위와 제외 구간은 [Redis 캐시 전략](../design/redis-cache-strategy.md#캐시-재생성-시간-관측)을 따릅니다. 이후 실행의 계측값으로 과거 실패 원인을 소급 증명하지 않습니다.

### 재측정과 완료 판정

현재 고부하 재측정은 호스트 메모리 여유 부족과 테스트 컨테이너 종료로 보류했습니다. 컨테이너의 `OOMKilled=false`만으로 호스트 메모리 압박을 배제하거나 종료 원인을 확정하지 않습니다. 후보 비교와 최종값 선정은 미완료이며, 운영 시작값과 기존 오류 판정 기준을 유지합니다.

재개 시에는 실행 환경을 다시 기록하고 새로운 결과 이름을 사용합니다. k6 종료 코드, 클라이언트 완료 건수, 예상 밖 오류, Outbox/Inbox/Audit 수렴과 정합성 SQL 결과를 함께 보존합니다. 검증 파일이 누락된 실행은 정합성 통과로 처리하지 않으며, 서버 측 후속 처리가 수렴하더라도 클라이언트 완료 기준 실패를 통과로 바꾸지 않습니다. k6 threshold 미충족은 실패라는 [공식 기준](https://grafana.com/docs/k6/latest/using-k6/thresholds/)도 그대로 적용합니다.

상세 후보와 원본 수치·실행 로그는 Git 제외 private 자료에 유지합니다. #71은 재측정과 최종 설정 검증이 끝날 때까지 열어 둡니다.

## 2026-09-11 후보 반복 측정 및 최종 재검증

중단됐던 후보 측정을 재개해 두 후보를 각각 3회 검증했습니다. 본 측정 6회 모두 클라이언트 결제 완료 1,000건, unexpected 0건, Outbox/Inbox/Audit 각 1,000건 수렴과 확장 SQL의 정합성 오류 0건을 충족했습니다. 후보별 설정과 상세 수치는 private 자료에 보관합니다.

이후 Docker 재기동 뒤 기존 설정을 워밍업하고 본 측정 3회를 실행했습니다. 첫 본 측정은 클라이언트 완료 기준에 미달했고, 나머지 2회는 완료·수렴·정합성 기준을 통과했습니다. 따라서 최종 기준 설정의 3회 전부 통과를 확인한 것은 아니며, #71은 미완료 상태로 유지합니다. 실패한 본 측정을 워밍업으로 재분류하거나 제외하지 않았습니다.

### 선택과 한계

- 기존 Relay batch `20`, Consumer idle `0ms`를 유지합니다. 최적값을 입증한 선택이 아니라, 운영값을 바꿀 만큼 재현 가능한 개선 근거를 확보하지 못한 판단입니다.
- Relay의 batch를 줄이면 한 번의 실행이 처리하는 작업량은 줄지만, 동일 backlog에 필요한 실행 횟수와 실행 사이 `fixedDelay` 대기가 늘어납니다. 요청 여정 지연과 감사 기록 수렴 시간을 함께 평가해야 합니다.
- Consumer 대기를 추가한 후보도 정합성은 통과했지만, 실행 순서에 따른 성능 편차가 남아 있어 대기 추가만의 효과를 분리하지 못했습니다.
- 날짜와 Docker 재기동이 다른 실행 묶음을 하나의 통제된 성능 비교로 합치지 않습니다. 이번 결과는 제한된 조건의 검증이며, 신규 설정의 성능 우위를 주장하지 않습니다.

### 남은 검증

다음 작업은 후보 수를 늘리는 것이 아니라 **기준 설정의 재기동 후 반복 측정 재현성 확보**입니다. readiness의 유휴 CPU·DB 대기·backlog 확인과 실제 부하 경로의 워밍업 완료를 구분하고, 측정 전에 정한 준비 조건을 동일하게 적용해야 합니다. 이번 측정에서는 timeout, 캐시 TTL, 풀 크기, 완료 기준을 완화하지 않았습니다.

중단 지점을 확인할 수 있도록 로컬 실행 도구에 단계별 checkpoint, 결과 이름 중복 방지, null hash를 포함한 수렴 검증을 보강했습니다. 로컬 테스트 설정·토큰·원본 결과는 Git에 포함하지 않습니다.

## 2026-09-13 진단 세이브포인트

### 완료한 작업

- 기존 측정 이미지를 재사용해 재기동 후 첫 부하를 JFR(Java Flight Recorder)과 Prometheus로 관측했습니다. 이번 진단에서는 이전 완료 건수 실패가 재현되지 않았고 결제·이벤트 수렴 및 정합성 검증을 통과했습니다. 최신 dev 전체를 다시 검증한 결과는 아닙니다.
- 원본 JFR을 순차 처리해 JVM 컴파일·GC·스레드 대기를 분석했습니다. 대용량 변환 JSON 전체를 메모리에 올리지 않고 필요한 통계만 추출했습니다.
- HTTP 스레드의 Hikari 대기 중 만료 후보 조회와 JWT 인증의 사용자 조회 경로를 확인했습니다. 스택의 소스 라인까지 대조해 인증 필터의 후속 요청 위임이 아니라 실제 사용자 조회 위치임을 구분했습니다.
- 진단용 JFR 옵션을 제거하고 기존 Relay·Consumer 설정으로 복원했습니다. 애플리케이션 코드와 인증·최신성 정책은 변경하지 않았습니다.

### 아직 확정하지 않은 것

관측한 것은 **커넥션을 기다린 호출 경로**입니다. 커넥션을 오래 점유한 원인, 느린 SQL, 풀 크기 부족, JIT 또는 Kafka 단독 원인을 확정한 것은 아닙니다. 스레드별 대기 시간과 컴파일 경과시간의 합을 단일 요청 지연이나 CPU 점유율로 해석하지 않습니다.

JFR 기록은 추가 관측 비용이 있으므로 이번 실행을 성능 합격 기준선으로 대체하지 않습니다. 이전 실패 기록과 #71의 미완료 상태를 유지합니다.
